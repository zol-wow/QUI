QUI · Aura Displays UX — Unified Design (implemented)
Unified design · shipped in the addon

Three doors,
one editor.

Approaches 1 + 2 + 3 combined and implemented: Templates for instant value, a Guided wizard for intent-first creation, and Simple Mode so the editor you land in afterwards doesn't drown you. All three produce ordinary Displays, editable in the same 3-tab detail pane (General / Auras / Load Conditions).

Recap

What was combined — and what was deferred

Five approaches were explored (decks 01–05). Three ship now as one design; two are deliberately deferred, not rejected.

SHIPPED

01 · Guided wizard → Guidance

Intent-first creation: "what do you want to track?" before any settings. Ships as the Guided tab of the New Display dialog — 4 steps, goal → spell → look → place.

SHIPPED

02 · Templates → Discovery

Ship content, not blank forms. Ships as the Templates tab (the default): ~8 curated starters, one click each, fully configured and positioned.

SHIPPED

03 · Simple Mode → Mastery

The editor stays learnable: a summary sentence per element, essentials always visible, everything else in collapsed sections. Ships as a simpleMode capability on the shared editor.

  • 04 · Canvas — deferred: direct-manipulation editing is a large rendering investment; the 3×3 zone picker plus existing anchor records cover placement for now.
  • 05 · Recipes — deferred: the sentence UI shipped as read-only output (the Simple Mode summary sentence) rather than as an input language; per-display share strings would come with it.
Why these three

The doors reinforce each other

Each door hands the user to the next one. Same data model everywhere — nothing forks.

Door 1 · Discovery

Templates

Show what the feature can do. One click installs a working display — the feature demos itself before the user configures anything.

→
Door 2 · Guidance

Guided wizard

Teach intent → settings for the user's own ideas. Four questions produce a configured display and quietly show which settings encode which intent.

→
Door 3 · Mastery

Simple Mode

Keep the editor learnable when the user tweaks the result. The summary sentence names what each setting does; the full control set is one section-header away.

One data model. A template is just a serialized display. The wizard's output is just a display. Simple Mode is a rendering order, not a fork — no "simple displays" vs "advanced displays", no migration, no dead end.

Door 1 · New Display dialog

Templates tab — the default landing

Templates relevant to your current role sort first. One click on Add installs a fully configured display — 32 px icons, duration text on, sorted, positioned via a screen-zone preset — and selects it in the list.

↳ click the tabs, or click "Add" on a template

Generic by design

Templates are built from Blizzard's aura classifications — dispellable, boss, loss-of-control, only-mine, stealable — not from curated per-spec spell lists. So they never rot when a patch reshuffles spells.

  • Row anatomy: icon · name · one-line description · meta (STRIP badge · unit · e.g. "Load: Tanks")
  • "Recommended for you" group keyed off current role
  • Installed display is an ordinary Display — edit or delete it like any other
  • Add is idempotent-friendly: adding twice just makes a second copy with a numbered name
Door 1 · New Display dialog

Custom tab — the power-user escape hatch

The old quick-create form survives intact as the third tab: two clicks from anywhere, zero ceremony. It now inherits the fixed defaults like every other path.

↳ toggle Track spells / Filter strip, then click Create

  • Track spells | Filter strip segmented control
  • Spell ID + Browse, Name, Unit — nothing else asked
  • Creates with the same 32 px / duration-on defaults (the 16 px bug is dead — slide 11)
  • Retained as the fallback path if the dialog module ever fails to load
Power users lose nothing: the Custom tab is the exact form they already know, one tab-click away from the Templates default.
Door 1 · Guided tab

Guided wizard — goal first, spell second

Step 1 asks what, not how: six goal cards map straight onto element configurations. Step 2 branches — tracked goals get a spell-ID input with live name echo; strip goals get a pre-selected, editable "What to Show".

↳ pick a goal card, then Next — walk all four steps to Create

Goal → configuration

  • A buff or proc on me → tracked · Only My Cast
  • My debuff on my target → tracked · HARMFUL · unit Target
  • All my short buffs → filter strip · only mine
  • Debuffs I can dispel → strip · dispellable
  • Boss debuffs on me → strip · boss auras
  • Another player's auras → unit-focused strip
The card copy names the intent; the fine print names the mechanism. Users learn the intent→settings mapping just by reading the cards.
Door 1 · Guided tab

Look, place, load — then Create

This instance is seeded from steps 1–2 (goal: a buff on me · spell: Renewing Mist 115151). Step 3 picks display type and size; step 4 names it, places it on a 3×3 screen grid, and sets load conditions.

↳ pick a look and size, Next, then place it and click Create Display

  • Display type cards — Icon / Bar / Colored Square (tracked goals only)
  • Size presets S / M / L = 24 / 32 / 40 px
  • Name auto-filled from the spell; unit pre-set by the goal
  • 3×3 zone picker writes a real frameAnchoring record — no dead-center spawns
  • Load: Always / My class only / My spec only → the same display.load sets as the Load Conditions tab
  • "Create Display" lands you in the editor with everything set

Door 2 · the editor

Implementation

Where it lives

Data and UI are split so the interesting logic is testable without a WoW client.

modules/trackers/aura_display_templates.lua ← NEW ns.QUI_AuraDisplayTemplates template list + goal list + pure builder functions UI-free → unit-testable headless modules/trackers/settings/aura_displays_create.lua ← NEW ns.QUI_AuraDisplaysCreate — the 3-tab dialog wired into the existing "New Display" button in aura_displays_content.lua old popup retained as the Custom tab / fallback QUI_Options/aura_elements_editor.lua ← CHANGED new simpleMode capability + summaryUnit string passed only by the Aura Displays page; other hosts pass neither → render exactly as before
  • Element construction reuses E.NewTrackedElement / E.NewFilterStripElement / E.ApplyWhatToShow
  • Load gating writes the same display.load.{classes,specs,roles} sets as the Load Conditions tab
  • Positions use existing frameAnchoring records + QUI_ApplyFrameAnchor
  • Unit tests: template installation validity · wizard spec building · summary-sentence builder
  • New ns.L strings go through QUI's i18n regen pipeline
Capability gating means Group Frames, Unit Frames, and Nameplates — which share the element editor — are untouched. Simple Mode cannot regress them because they never opt in.
Scope

Deliberately not in v1

Each cut has a natural follow-up path — nothing here is architecturally foreclosed.

  • Per-display share strings — templates prove the serialization shape; export/import of that same shape is the obvious next increment.
  • Spec-curated spell suggestions in wizard step 2 — the spell-ID input works today; a curated suggestion list per spec can slot into the same field once there's a maintenance story for it.
  • Canvas editing (deck 04) — the 3×3 zone picker + frameAnchoring already position displays; drag-on-screen editing can layer on top of the same anchor records later.
  • Recipes (deck 05) — the summary sentence ships read-only; making it editable (sentence-as-input) is the follow-up once the sentence vocabulary has proven itself.

The bet, restated

Discovery → guidance → mastery, over one data model. Templates get users to value in one click; the wizard teaches the mapping from intent to settings; Simple Mode keeps the full editor approachable. Everything created is an ordinary Display — so power users, sharers, and future features all meet in the same place.
