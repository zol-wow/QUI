Approach 3 of 5 · Sentence-first progressive disclosure

Simple Mode

Same power, 11 visible things instead of 46.

Don't build a new surface. Rebuild the information hierarchy of the editor we already have. Every element renders first as one editable plain-language sentence, then ~6 essential controls, then everything else behind counted "Advanced" disclosures. A pinned live preview shows what you're editing at all times. Advanced is today's full editor — nothing is removed.

The problem today

Every element opens as a wall of rows

In Auras → Aura Displays, clicking an element row on the Auras tab expands an inline form. A Filter Strip fronts ~46 rows across Basics / Filters / Appearance & Advanced — and grows past 70 with Filter Mode set to Classification or Flags, Dispel Type Filter, custom borders and tooltips enabled. Nothing tells you which six of those rows actually matter.

The pain, in numbers

  • ~35–40 controls front a minimal new display (General tab alone has 23 options).
  • 80–120 widgets on screen for a two-element display.
  • A TRACKED element form is ~31 rows; a FILTER STRIP is ~46, up to 70+.
  • Quick-created displays start at 16px icons with duration text OFF — even though good defaults exist in AD.DefaultBucket (32px, 12pt). Quick-create discards them.
  • The Preview toggle exists in the detail-pane header, but it's off to the side of the wall, not part of the editing loop.
Users don't fail because a setting is missing. They fail because the six settings that define the element are visually equal to the forty that refine it.
The core idea

Three tiers, one editor

Same detail pane, same tabs (General / Auras / Load Conditions), same element rows with STRIP / TRACKED badges. Only the expanded form changes: it renders in strict order of importance.

Tier 1 — The sentence. What this element is.

"Show an icon of Renewing Mist on Player — only my cast." Every bold token is an inline dropdown. Reading it teaches the data model; editing it edits the element.

▼

Tier 2 — Essentials. The ~6 controls people actually touch.

Size · Duration text · Stack text · Glow · Position · Sort (strips). Chosen per element kind, iterated from usage.

▼

Tier 3 — Advanced. The other 25–60, collapsed and counted.

"Appearance · 12 more settings ▸" — click to expand exactly today's rows. Plus a settings-search box that finds any of them by name. Nothing is dumbed down; it's the same editor, resorted.

Not a fork. Simple/Advanced expansion state is remembered per user. Power users who open everything once live in the full editor forever. New users see 11 things.

Why a sentence? It's self-documenting. "Debuffs (Harmful)", "Only My Cast", "Unit" are today four unrelated dropdowns; in a sentence their relationship is grammar. New users learn the model just by reading the default: "Show an icon of Renewing Mist on Player — only my cast."
Same data underneath. Every token maps 1:1 to an existing setting (Display Type: Icon / Colored Square / Bar; Aura Type; Only My Cast; Unit from the General tab). The sentence is a render order, not a new schema.
Walkthrough 2/5 · The sentence editor

A FILTER STRIP, as a sentence

Strips are the scary form — 46 rows. But their essence is five decisions: how many, what kind, on whom, filtered how, growing which way. The sentence fronts exactly those, wired to today's "What to Show" presets.

STRIP  My HoTs ▲ collapse
Show up to 8 buffs on Player matching Only my auras, growing right

↳ click to try it — max icons, aura type, filter preset and grow direction all cycle

"matching Only my auras" is the existing What to Show list verbatim: All · Only my auras · Defensives · Important · Purgeable · Dispellable by me · Crowd control · Boss debuffs · Role-relevant boss debuffs · Specific spells · Custom… Picking Custom… is the escape hatch — it opens the Filtering advanced section (Filter Mode, Filter Flags, Classification, whitelist/blacklist editors).
Escape hatch rule: any combination the sentence grammar can't express renders as "matching Custom filter (4 rules)" — a token that jumps straight to Advanced. The sentence never lies; when it can't summarize, it says so and hands over.

Defaults are part of the design

Honest scorecard

What this fixes — and what it doesn't

Fixes

  • Overwhelm. 46 equal-weight rows become 11 ranked things. First-session success rate is the metric.
  • Teaches the model. The sentence explains Aura Type / Unit / Only My Cast / What to Show by using them in grammar, not in a wiki.
  • Findability. Settings search + counted sections replace scroll-and-squint.
  • Cause and effect. Pinned live preview keeps every edit visibly consequential.
  • One surface. No wizard, no second editor to keep in sync — Advanced is the current editor.

Doesn't fix

  • Discovering WHAT to build. No content, no templates, no "Mistweaver starter pack". A blank display is still a blank display. (That's approaches 2 and 5.)
  • Exotic combos read badly. "Show up to 12 debuffs matching Filter Flags ∩ Classification minus 14 blacklisted spells…" — the grammar breaks. Needs the explicit fallback: unparseable elements render as "Custom filter (n rules)" and route to Advanced only.
  • i18n is real work. Sentence templates with movable token slots must go through QUI's ns.L system per locale — word order differs, and new strings need the i18n/search-cache regen step. Budget for it; don't string-concatenate.
  • Essentials selection is opinion. The "right six" per element kind will be wrong on the first pass and needs iteration against real usage.
Implementation notes

This is a re-sort, not a rewrite

  • The editor is already shared across Aura Displays / Group Frames / Unit Frames / Nameplates via a capability system in QUI_Options/aura_elements_editor.lua (2095 lines) that gates whole controls per host. A simpleMode capability is the same mechanism pointed at a new axis: the precedent exists.
  • Work = rendering order + tiering metadata per control (essential / advanced-section / sentence-token), plus the sentence renderer and the search index over control labels.
  • The preview infrastructure exists (the On/Off toggle in the detail-pane header) — pinning it and driving it from edits is incremental, not greenfield.
  • Per-user expansion memory is a handful of saved-variable booleans keyed by section.
  • Ship order that de-risks: (1) DefaultBucket applied to quick-create, (2) sections + counts + search, (3) essentials tier, (4) sentence renderer last — it's the most valuable and the most speculative.
Verdict

Steal this if the editor itself is the product and you want one surface, not two.

It makes the existing editor learnable without forking it, and its cheapest pieces (defaults, sections, search) are worth stealing even if the sentence editor never ships. It will not, on its own, tell a fresh Mistweaver what displays to build — pair it with a content-side approach for that.
