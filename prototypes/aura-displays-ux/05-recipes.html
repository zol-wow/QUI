Approach 5 of 5 · Design pitch

Intent Interview + Recipes

Answer questions, learn the machine — the interview shows its work.
One plain-language question at a time on the left; a live “build sheet” of the real settings it configures on the right. The same engine powers one-click recipes that modify existing displays.

Conversational

One decision per screen. Branches on your answers — not a linear form.

Transparent

Every answer writes visible lines to the build sheet, grouped by the real tabs.

Not just for creating

Recipes apply intent-level changes to displays you already have.

Navigate: ← / → arrow keys, dots bottom-right. Mock screens are clickable.

The problem today

One sentence of intent = six settings across two tabs

Aura Displays (Auras tab → sub-tab 6) is powerful, but the surface area is brutal — and nothing maps what the user wants to which controls express it.

Six decisions, two tabs, and the user must already know STRIP vs TRACKED, that Unit defaults matter, and where Duration Text lives. Nothing in the UI teaches this mapping. That gap — not any single control — is what keeps people on WeakAuras imports.

Core idea

Interview → build sheet → recipes: one intent engine, three faces

Turn plain language into real settings — and never hide the translation.

1 · Interview

One question at a time, branching

“What should this react to?” Three big answers. The next question depends on the last answer — a spell path and a category path are genuinely different conversations.

→
2 · Build sheet (the hero)

A live settings receipt

Every answer appends real setting lines — Tracked Spells: 115151, Icon Size: 32 — grouped under General / Auras / Load Conditions, the actual tab names. You learn where things live while answering.

→
3 · Recipes

Intent-level edits, forever

The same engine runs in reverse on existing displays: “Glow when about to expire” → a confirm-diff of the 3 settings it will change. Value doesn’t end after creation.

Why this isn’t “a wizard with extra steps” (see Approach 1)

  • Branching, not linear: one decision per screen; the tree adapts. A linear form shows you fields you don’t need.
  • Teaching, not hiding: the build sheet exposes the model. Wizard users stay wizard users; interview users graduate to the full editor.
  • A modification tool, not just a creator: recipes work on any existing display — including ones the interview never touched.

Why the recap matters

This is the anti-black-box move. The user leaves with a mental model: “my answers became these 11 settings, and they live under these 3 tabs.” Next time they may skip the interview entirely — that’s the goal, not a failure.

“Ask another way” = the dead-end exit

Every branch keeps two escape hatches: restart the interview, or Open in editor with everything so far pre-filled. A question tree must never trap anyone.

Not possible today — and we say so.
Aura Displays has no chat/sound output and no “aura missing” trigger state. Faking it with a hidden always-on strip would lie about what the engine does. The recipe stays visible but honest: it names the missing capability so it can become a real feature request instead of a support ticket.

The confirm-diff is non-negotiable: recipes touch a display the user may have hand-tuned. Before→after values, then Apply — with Undo. Same trust move as the build sheet.

Why bolt this on?

The recipe library and the interview’s answer→settings mapping are already keyword-indexed content. Feeding them to the existing options search is nearly free — and it’s where confused users already go first.

Diagnosis, not just lookup

“Icon huge in combat” can cross-reference actual display records: which display has a large Icon Size and combat-scoped Load Conditions? That’s an answer, not a search hit.

Honest assessment

What it fixes — and what it doesn’t

What it fixes

  • Bridges the intent→settings gap directly. “Show my defensive when active” becomes 5 clicks instead of 6 settings across 2 tabs.
  • Teaches instead of hiding. The build sheet uses real setting names under real tab names — users graduate to the editor rather than depending on the tool.
  • Ongoing value after creation. Recipes work on existing displays forever — the other four approaches mostly stop mattering once a display exists.
  • Fixes bad quick-create defaults for free. Interview output goes through one curated defaults path (finally putting AD.DefaultBucket-quality defaults to work) — no more 16px icons with duration text off.
  • Honesty is built in. Confirm-diffs, AUTO tags, and “not possible” recipes keep trust intact.

What it doesn’t — the real costs

  • Content is the hard part. Authoring and maintaining the question tree + recipe library is significant, ongoing design work. The engine is cheap; the writing isn’t.
  • Branching trees can dead-end. Any intent the tree doesn’t cover hits a wall — every screen must keep the “Open in editor” exit, pre-filled with progress so far.
  • “When it’s missing” may exceed the engine. Inverse displays aren’t clearly supported today; the interview must flag it (as mocked on slide 5), not fake it. Same for “announce when missing”.
  • Doesn’t shrink the editor. The 80–120 widget detail pane is untouched — this is a ramp onto it, not a replacement. Pairs naturally with approaches 2–4.
  • Slower for experts. Five screens vs. one dense form. Experts need a skip-to-editor path from question one.
Implementation notes

Cheap engine, content-shaped cost

Nothing here needs new display-engine capability (except the flagged “missing aura” path).

Interview output = a plain display record

The finish screen just calls the existing NewDisplay path plus the existing element constructors (STRIP / TRACKED) with the accumulated settings table. No parallel data model, no interview-specific persistence — “Open in editor” is trivially correct because there is only one record.

Recipes = declarative setting-patches

A recipe is a name, keyword list, applicability predicate (e.g. needs a TRACKED element), and a list of {path, value} patches. Confirm-diff and undo fall out of that shape for free. The engine is a weekend; the library of good recipes is the real investment.

Build sheet labels = existing options metadata

Setting display-names and tab grouping already exist in the options metadata / search index — the build sheet renders from it, so labels can’t drift from the real panel. The “Ask the panel” surface indexes recipe keywords into the same search.

Suggested build order

1. Recipe engine + 5 recipes with confirm-diff (standalone value, smallest risk) → 2. Interview spell-path only, reusing recipe patches as its vocabulary → 3. Category/STRIP branch + unit branch → 4. Search integration. Each step ships alone; the interview is never blocked on covering every intent.

Verdict

Steal this if you want new users to graduate into power users — instead of staying dependent on wizards.

The build sheet is the idea worth stealing even if nothing else survives: any guided flow QUI ships should show its work in real setting names. It costs one panel and buys a teaching tool, a trust signal, and a map of the editor.

Steal whole

Build sheet + confirm-diff recipes. Both are engine-cheap and compose with any other approach in this series.

Steal partially

The interview’s spell path alone (Q1→spell→look→conditions) covers the single most common intent and fixes quick-create defaults as a side effect.

Skip if

No appetite for ongoing content authoring — a stale question tree or thin recipe library is worse than none, because it teaches users the tool can’t help them.
